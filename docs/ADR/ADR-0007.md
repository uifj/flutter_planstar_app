# ADR-0007: 精选推荐、场地页、保障条与榜单兜底为本地派生，无对应端点或仅覆盖首屏

- **状态**: PROPOSED
- **分类**: DEF
- **优先级**: P2
- **影响维度**: 生产功能 / 幻觉源
- **日期**: 2026-11-16
- **来源**: 全量接口审计
- **修复 commit**: —

## 背景（Context）

首页/场地/榜单存在一批"看起来来自服务端、实则前端派生"的数据，均无专用端点：

- **精选推荐按分类聚合**：[catalog_providers.dart#L385-L410](../../lib/features/catalog/application/catalog_providers.dart#L385-L410) 的 `choicenessGroupsProvider` 对 `cityShowsProvider` 按 `categoryId` 分组、按想看数排序后每类取 8 条。真实模式下 `cityShowsProvider` 直接指向分页的 `showCatalogProvider`（[#L274-L287](../../lib/features/catalog/application/catalog_providers.dart#L274-L287)），未触底时只有第一页 20 条，因此"精选"楼层可能整类缺失。
- **场地页聚合同城企划**：[catalog_providers.dart#L477-L488](../../lib/features/catalog/application/catalog_providers.dart#L477-L488) 的 `venueShowsProvider` 在已加载列表里 `where(show.venue == name)`；[venue_page.dart#L44](../../lib/features/goods/venue_page.dart#L44) 直接消费。后端无 `GET /v1/venues/{name}` 或按场地查询的端点。
- **热门楼层本地兜底**：[home_page.dart#L154-L159](../../lib/features/home/home_page.dart#L154-L159) 在 `hotShowsProvider` 失败/首帧时用当前列表按 `wishCount` 排序兜底。
- **Banner 本地兜底**：[home_page.dart#L178-L194](../../lib/features/home/home_page.dart#L178-L194) 在 `v1/home/banners` 为空时用本地渐变卡与固定文案构造 `BannerSlide`（含固定 `badge: '推荐'`）。
- **榜单本地排序兜底**：[catalog_providers.dart#L371-L381](../../lib/features/catalog/application/catalog_providers.dart#L371-L381) 的 `projectRankingProvider` 在 demo 或请求失败时返回空列表；[ranking_page.dart#L100-L119](../../lib/features/home/ranking_page.dart#L100-L119) 与 [home_ranking_floor.dart#L95](../../lib/features/home/widgets/home_ranking_floor.dart#L95) 随即改用 `rankShowsLocally(shows, _type)` 本地排序。
- **保障条为静态文案**：[home_guarantee_floor.dart#L23-L30](../../lib/features/home/widgets/home_guarantee_floor.dart#L23-L30) 的 4 条保障全部来自 l10n 常量，不可配置。

用户可见影响：真实模式下"精选推荐"可能只显示部分分类（首屏 20 条内的分类），且没有加载更多；场地页在没有同城已加载数据时为空，即使服务端存在该场地的企划；榜单排序口径在前端本地与服务端之间不一致；保障文案无法运营调整。

## 决策（Decision）

候选方案：

- **A. 后端补专用端点**：`GET /v1/choiceness`（运营可配的分类精选）、`GET /v1/venues/{id}/projects`、`GET /v1/home/guarantees`（或合并进首页聚合接口）。**需后端/运营协作**。
- **B. 前端修正数据来源，不新增端点**：精选改为直接使用 `showFeedProvider` 按分类分页（已有服务端筛选能力）；场地页改为进入时按 `city` + 已加载分页续拉，或明确空态文案；榜单兜底时展示"本地排序"标识；保障条保留静态但确认运营接受。
- **C. 保持现状并加注释说明**。

选定：**B 立即执行 + A 作为中期目标**。理由：精选/场地的问题本质是"在单页缓存上做全量聚合"，用已有的 `showFeedProvider(categoryId:)` 分页即可消除"分类缺失"，无需等待新端点；保障条作为品牌文案可接受静态，但需运营确认；A 仅在需要运营配置化时再排期。

## 后果（Consequences）

- **正面**: 精选楼层与场地页不再受首屏 20 条限制；榜单在兜底时有明确标识，减少"排序口径不一致"的困惑。
- **负面/风险**: 精选改为按分类分页会增加首屏请求数（每个分类一次），需限制首屏分类数或串行/并发控制；场地页分页需要处理滚动加载。
- **中性**: `ChoicenessGroup` 等展示模型可保留；A 落地时仅替换数据源。

## 验证（Verification）

```bash
# 后端无精选/场地/保障专用端点（A 落地后应命中）
rg -n 'choiceness|venues|guarantees' planstar_kratos_server/planstar/internal/service/service.go

# 前端派生点
rg -n 'choicenessGroupsProvider|venueShowsProvider|rankShowsLocally' flutter_planstar_app/lib
```

- 真实模式手测：首页"精选推荐"在对应分类有数据时不再整类缺失；滚动时可继续加载。
- 真实模式手测：`/venue/:name` 在有该场地企划时能展示，且滚动可加载更多；无数据时展示明确空态而非"加载中"。
- 榜单在服务端不可用时展示"本地排序"标识，与服务端榜单可区分。
